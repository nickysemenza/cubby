### Product price footer experiment

An isolated PostgreSQL integration database held 1,000 synthetic Products, 10,000 positive principal Expenses (10 per Product), and 999 `productComponent` links: 990 leaves under nine inner kits, then those nine kits under one outer kit. The harness bulk-inserted these rows, ran `ANALYZE` on Product, Expense, and EntityLink, then timed `loadProductPriceSum` over 20 warm calls. It also ran `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` on the exact footer SQL. The filter was all live Products; a second probe selected one leaf. No production data or application result cache was used. The temporary benchmark harness was removed after measurement so it does not add 10,000-row setup to the normal integration suite. To reconstruct, use the stated fixture shape in an isolated test database, call `loadProductPriceSum(db, notDeleted(product))` and `loadProductPriceSum(db, and(notDeleted(product), eq(product.shortcode, "PRD-BENCH000011")))` 20 times each, and explain `productPriceSumSql` before/after this change.

The full-filter query's `EXPLAIN ANALYZE` execution time fell from 860 ms in the first analyzed baseline (464 ms on repeat) to 10.7 ms after grouping. That is PostgreSQL execution time, separate from the request timer above. A SQL `CASE` that selected the old scalar path below five matches improved the one-leaf case to 1.16 ms but made the full-filter case 584 ms (532 ms in `EXPLAIN`), apparently from planning/JIT overhead; it was reverted. A prior batch-loader experiment grouping siblings or Expenses across a small 67-product fixture also regressed (correlated median 12.07 ms; grouped siblings and Expenses 24.49 ms; Expenses alone 12.97 ms) and was reverted. Thus the grouped path is confined to the full-filter footer; page-size pricing, sort, and filter scalar paths remain correlated. The retained footer pays about 2 ms for a one-leaf filter but removes about 430 ms for the broad filter in this synthetic fixture. These timings do not establish production latency or pool-wait savings; the final revision still needs a live request trace.

These are **test-run durations, not request latencies**. A separate picker/task integration batch passed those files. ## Remaining static candidates

1. **Project dashboard fanout.** [`projectDashboardSummary`](../apps/web/src/server/repo/project/dashboard-summary.ts) first loads whole-tree rollups, then launches nine reads, then another batch of scoped aggregates and a final task hydration batch. Some depend on the scoped project IDs or date windows, but the unscoped filter-option scans can be considered for earlier overlap or consolidation. The existing pool limits concurrent SQL; count round trips and queue time on a representative filtered and unfiltered request before changing the query shape. Preserve subtree-inclusive totals, scope-root deduplication, date chips, and `nextTasks` semantics.
2. **Expense analytics fanout.** [`expenseAnalytics`](../apps/web/src/server/repo/expense/analytics.ts) runs eight aggregate reads for one filter set. They can queue behind the pool even though the JavaScript uses `Promise.all`. A shared grouped scan or conditional aggregates may reduce trips, but only an `EXPLAIN (ANALYZE, BUFFERS)` and elapsed/CPU comparison can establish a gain. Preserve negative credits, nullable dates, allocation-scoped totals, and the exact list filter population.
3. **Location valuation stages.** [`loadLocationValuationInputs`](../apps/web/src/server/repo/location/valuation.ts) obtains inventory valuations, inventory rows, location rows, then linked-product prices. The location row scan is independent of inventory valuation and row loading; it may overlap those stages. Product-price loading still depends on location product IDs. Compare actual round trips and pool occupancy before widening concurrency. Whole-tree rollup and fixture-versus-stock semantics must remain intact.
4. **Grouped search expansion.** [`findGroupedSearchHits`](../apps/web/src/server/services/search-grouping.service.ts) may fetch a larger candidate set and re-compose groups when the first batch collapses below the requested limit. This can repeat relation, placement, and image work. Measure how often expansion occurs and where time is spent before changing it; exact shortcode handling, ranking, and grouping determine when a larger batch is necessary.
5. **Graph frontier batches.** [`exploreEntityGraph`](../apps/web/src/server/repo/entity-graph-explore.ts) awaits each chunk within a frontier. Chunks at the same depth may be independent, but read/deadline budgets and deterministic path ordering constrain safe concurrency. Treat this as an experiment gated by a graph fixture and latency trace, not a blanket `Promise.all` change.
6. **Whole-board and date-picker populations.** [`task.board`](../apps/web/src/server/repo/task/board.ts) requests all matching active top-level tasks with a high page cap, while [`projectNameOptions`](../apps/web/src/server/repo/project/lookup.ts) computes effective dates over all live projects for date-aware pickers. Both have deliberate completeness contracts. Record row counts, bytes, query time, and hydration time on realistic synthetic data before considering a different projection or bounded UI behavior.

The project dashboard has no readily available standalone CPU harness in this checkout that reproduces its database, allocation, and subtree work without the shared PostgreSQL test service. No local CPU profile was attempted. The next measurement should capture one sanitized request per family with revision, operation/input shape, read-policy choice, pool wait, SQL count and duration, server CPU, response bytes, and client-visible completion. That would distinguish database execution from freshness routing, connection contention, hydration, and rendering without guessing from source structure.

## Final implementation validation

The retained changes route ordinary queries through the authoritative pool, overlap independent product/search/tree hydration, reuse task and expense scopes and picker date windows, and construct project inheritance maps once per tree load. Product batch/scalar pricing retains its original query shape; only the full-filter footer uses grouped live siblings and visited-ancestor expenses.

Rows, counts, groups and totals share ID restrictions before pagination, including inventory’s custom WHERE builder. Purchase totals sum linked live Expense lines; expense list totals sum raw ledger costs, while project allocation analytics are labeled separately. Declaration-owned totals drive web table/card summaries, native Browse/search summaries, and CLI text/opt-in JSON metadata. Missing totals are unavailable; zero and credits remain values. Filter transitions clear previous-population totals.
